# 게임필(Game Feel) 진단 — 윷놀이 "딱딱함" 코드 감사

- 날짜: 2026-08-11
- 대상: `public/yut.html`(렌더·연출·인라인 코어) + `public/yut-core.js`(엔진)
- 문제 제기: 재성님 — "모바일 웹에서 너무 딱딱하다(stiff), 특히 윷놀이는 재미가 반감될 정도"
- 성격: 규칙/색/레이아웃이 아니라 **손맛·연출·피드백·템포(juice)** 문제
- 목표 품질: 한게임·넷마블 급
- 방법: 실제 코드 근거(파일:라인). 확인 못 한 것은 [확인필요].
- 제약: 이 문서는 진단·제안만. 코드는 수정하지 않음. 기존 아키텍처(단일 HTML+인라인 코어·빌드/드리프트·성능 예산 함정 34·reduced-motion 접근성) 존중.

---

## 요약 — 먼저 결론

윷놀이는 **연출이 없어서 딱딱한 게 아니다.** 오히려 던지기 손맛(파워 게이지+찬스 스윗스팟), 결과 풀스크린 버스트, 콤보, 말풍선, 햅틱, 합성 사운드/BGM, 잡기 튕겨나가기까지 **매우 많이 juice가 들어가 있다.** 딱딱함은 세 군데의 **구조적 결함**에서 온다:

1. **말 이동이 칸마다 감속→정지하는 "로봇 행진"이다.** (가장 유력한 원인)
2. **reduced-motion이 켜져 있으면 위 연출이 전부 통째로 꺼진다** — 스위치 하나로 "재미 반감"이 그대로 재현된다. (모바일 최우선 확인 항목)
3. **죽은 대기 시간(dead time)이 길고, 그 동안 아무 피드백이 없다** — 뚝뚝 끊기는 stop-and-go 템포.

던지는 손맛 자체는 이미 좋은 편이므로, 개선 레버리지는 **① 말 이동 곡선 ② reduced-motion 절벽 완화 ③ 템포/대기 피드백**에 있다.

## 항목 1. 던지는 손맛 (윷 던지기)

### [현재 코드 상태] — 이미 상당히 잘 되어 있음

**흐름**: 버튼을 꾹 누른다 → 파워 게이지가 사인파로 0↔100% 왕복 → 뗀다 → 던지기 → 720ms 뒤 결과 공개.

- 파워 게이지 + "찬스(sweet spot)" 기믹: `yut.html:4470-4493`
  - `startGauge()`(4472): `gauging=true`, `.charging` 클래스로 캐릭터가 긴장(avTense)하는 anticipation. 게이지는 `Math.sin(el*Math.PI*2)`로 850ms 주기 왕복(4478).
  - `endGauge()`(4481): 뗀 파워로 찬스 구간(0.64~0.82) 판정 → `showToast('✨ 찬스!')` + 골드 플래시(4487-4488). `SFX.toss()`(4490) 후 액션 전송.
  - 파워는 엔진에서 윷·모 확률에 실제 반영: `throwYut(rng, power)` `th = 0.5 + (power-0.5)*0.26` (`yut.html:1698-1700`).
- **anticipation(기대감)**: `.charging`(캐릭터 긴장) + 게이지 왕복 = 릴리스 타이밍을 플레이어가 통제 → 능동적 긴장. 키보드 Space/Enter도 길게=게이지·짧게=0.5 (4499-4540).
- **결과 공개(payoff) 지연 연출**: `renderSticks()` `yut.html:4239-4279`
  - 윷가락 4개가 3D로 튀어 오르는 CSS 애니(`.stick.tossing`→`@keyframes yuttoss .72s`, `yut.html:729-730`): 위로 56px, rotateX 반 바퀴, 착지 시 앞/뒤 면 확정.
  - 던지는 캐릭터도 던지는 모션(`throwmo .68s`, `yut.html:720-721`).
  - **720ms setTimeout 뒤** 결과 텍스트 pop + `resultBurst()`(4262-4272) — 풀스크린 "윷이야!"/"모야!" 오버레이(`yut.html:3078-3099`, 레이·반짝이 파티클·카메라 펀치), 윷/모면 콤보 카운터(4275)·`SFX.yut()`+`BGM.duck()`(4270)·말풍선(4268)·큰 캐릭터 환호(reactCard, 4269).
- **사운드**: `SFX.toss()`(`yut.html:2492`)는 나무 부딪힘(woodClack, 밴드패스 노이즈 버스트) 5연타 + triangle 톤. WebAudio 합성 + 리버브 14% + 리미터(2478-2483). 결과는 `SFX.yut/backdo`. 외부 파일 0개.
- **햅틱**: `SFX.toss()`에 `buzz(18)`, 결과 `SFX.yut()`에 `buzz([30,20,50])`, `backdo`에 `buzz([15,50,15])` (`yut.html:2489-2500`). **음소거해도 진동은 유지**(soundOn 가드 밖).

### [딱딱함의 원인] — 던지기 자체는 딱딱하지 않다. 다만:

1. **첫 던지기의 사운드가 씹힐 수 있다 [확인필요].** AudioContext는 `SFX.toss()` 첫 호출(touchend 제스처) 안에서 생성·resume된다(`ac()`, 2475). 대부분 브라우저에서 동작하지만 iOS Safari는 "제스처 안에서 생성된 컨텍스트"의 첫 버퍼가 무음으로 나가는 사례가 있다. 첫 판 첫 던지기가 무음이면 "손맛 없다"의 첫인상을 만든다.
2. **차징 중 상승 피드백이 없다.** 게이지가 왕복할 뿐, 힘이 차오르는 **틱틱 소리·상승 피치·점증 진동**이 없다. 한게임/넷마블의 "충전형" 손맛은 게이지가 찰수록 소리/진동이 고조된다. 지금은 릴리스 순간에만 `buzz(18)`.
3. **찬스 구간이 "떼기 전엔" 시각뿐이다.** 게이지가 찬스 밴드(초록칸)를 지날 때 촉각/청각 신호가 없어, 정확히 언제 떼야 하는지 몸으로 못 느낀다(눈으로 초록칸을 봐야 함).
4. **위 모든 연출이 reduced-motion에서 통째로 꺼진다** → 항목 3 참조. `.stick.tossing` 애니 제거(`yut.html:940`), `resultBurst`는 정적만(`939-955`). 그러면 던지기는 "게이지 → 즉시 결과 숫자"로 밋밋해진다.

### [개선안]

- **A. 차징 상승 피드백(청·촉각).** `startGauge`의 rAF 루프(4478)에서 게이지 값 구간이 바뀔 때마다 짧은 틱(`SFX`에 `tick()` 하나 추가: 고역 클릭 8~15ms)과, 값이 찬스 밴드(0.64~0.82)에 **진입하는 순간** `buzz(10)` 한 번. 뗄 때 찬스면 지금처럼 강조. → 손이 "지금이다"를 느낀다. (사운드는 soundOn 가드 안, 진동은 밖.)
- **B. 첫 제스처에서 오디오 언락.** 게임 시작(첫 탭)에서 무음 버퍼 1개를 재생해 AudioContext를 미리 깨워, 첫 던지기 사운드 씹힘을 없앤다. `BGM.enter()`가 이미 컨텍스트를 만들지만(2578), **소리를 실제로 흘려보내는** unlock은 아님. `ac()` 직후 `tone(0,t,0.001,0)` 같은 무음 워밍업 추가. iOS 검증 [확인필요].
- **C. reduced-motion에서도 "결과 리듬"은 살린다.** 항목 3-C 참조 — 던지기는 애니 대신 **짧은 텍스트 카운트업/펀치 + 진동**으로 payoff 유지.

**주의**: 던지기 손맛은 이미 좋다. **A/B/C만으로 충분하며, 새 애니를 더 얹지 말 것**(과연출은 오히려 720ms 지연 위에 겹쳐 느려진다).

## 항목 2. 말 이동·잡기 연출  ★가장 유력한 딱딱함의 원인

### [현재 코드 상태]

- **이동은 칸 단위 hop이다.** `slideAlong(ids, path, hopMs, ...)` (`yut.html:3626-3657`):
  - `path`의 각 노드마다 `g.setAttribute('transform', translate(칸중심))` 후 `setTimeout(hop, hopMs)`. `hopMs = HOP_MAIN = 300` (`yut.html:3460`).
  - 위치 보간은 CSS 트랜지션 하나로: `#pieceLayer .pcpiece{ transition:transform .28s cubic-bezier(.4,.05,.3,1) }` (`yut.html:659`).
- **타이밍 상수**(`yut.html:3460`): `HOP_MAIN=300, HOP_EVENT=340, MOVE_PAUSE=1050, BANNER_MS=1150`.
- **잔상/먼지는 있다**: 지나온 칸에 `spawnTrail`(3510, 수명 480ms, 함정 7 색 규칙 반영), 최종 착지에 `spawnPuff`(3495, finish에서 3669).
- **잡기(상대 말 잡기)**: `runCaptureFx`가 착지 순간 상대 말을 튕겨 날린다(3393-3452), `SFX.capture()`+`buzz([25,30,45])`(2494), 멀티 잡기 배너(3314). 늪(pitfall)은 회전+낙하(660-661, `animatePitFall`), 완주는 떠오르며 골인(`animateFinish`, `.finishing` 663-664).
- **미사용 juice**: CSS에 **`@keyframes pcbump`(위로 7px 튀는 착지 바운스, `yut.html:688-689)`와 `.pcbody.hit`(pcHit, 713)이 정의되어 있으나, 일반 이동 경로에서 이 클래스를 붙이는 JS가 없다** (전체 검색: `classList.add('pcbump')` 없음). 즉 **디자인은 됐는데 배선이 안 됨.**

### [딱딱함의 원인] — 이게 핵심이다

1. **칸마다 감속→완전 정지→재가속 = 로봇 행진.** `cubic-bezier(.4,.05,.3,1)`는 각 홉에서 **ease-in-out**이라 매 칸에서 속도가 0으로 떨어진다. 게다가 `hopMs(300)`가 트랜지션(`.28s=280ms`)보다 20ms 길어, 매 칸에서 **20ms 정지**가 낀다. '걸'(3칸)=900ms, '모'(5칸)=1500ms 동안 **stop-go-stop-go**. 자연스러운 이동은 출발에서만 ease-in, 중간 칸은 등속 통과, 도착에서만 ease-out이어야 한다. 지금은 중간 칸마다 멈춰서 **가장 기계적으로 보이는** 방식.
2. **말이 평면으로 미끄러진다 — hop이 없다.** `slideAlong`은 `translate(칸중심)`만 바꾼다. 세로 hop 아치도, squash/stretch도 없다. 실제 윷 말은 통통 뛴다. 정의돼 있는 `pcbump`(3689)가 안 붙어서 **착지 바운스조차 없다.**
3. **긴 강제 정지(MOVE_PAUSE=1050ms).** 이벤트/늪/완주가 붙으면 메인 이동 후 1050ms를 그냥 배너만 보며 기다린다(3690, 3700, 3701). 뚝 끊기는 느낌의 큰 축.
4. (참고) 함정 6·7의 경로 스냅/reduced 문제는 이미 해결됨. 지금 문제는 "정확성"이 아니라 **"이동 곡선의 질감"**이다.

### [개선안]

- **A. 이동을 "연속 글라이드 + 칸마다 hop 바운스"로 바꾼다.** (체감 최대)
  - 방식 1(최소 변경): `pcbump` 배선만 살린다. `slideAlong`의 각 홉에서 `.pcbody`에 `pcHit`/`pcbump`를 재적용(void offsetWidth 후 add)해 **칸마다 통 튀는 착지감**을 준다. `.pcpiece transition`은 그대로. → 로봇 느낌 상당 완화, 코드 변경 최소.
  - 방식 2(권장, 더 자연스러움): 홉 단위 CSS 트랜지션을 버리고, **전체 경로를 하나의 rAF로 등속 보간**하되 위치 y에 `sin` hop 아치(칸 사이마다 위로 살짝)와 도착 이징을 얹는다. 카드 연출의 `CFX.fly` rAF 패턴(`cardfx.js:81-91`)이 그대로 참고가 된다. 출발 ease-in / 중간 등속 / 도착 ease-out + 칸 경계마다 hop → 한게임급 통통거림.
- **B. 착지 임팩트 강화.** 도착 칸에서 `pcbump`(이미 있음) + `spawnPuff`(이미 있음) + **짧은 `buzz(12)`**(현재 이동엔 진동 없음) + `SFX.move()`(2493, 지금은 잘 안 불림 [확인필요]). 잡기 없이도 "탁" 놓이는 맛.
- **C. 죽은 정지 시간 축소·차등화.** `MOVE_PAUSE`를 결과 종류별로: 일반 이동은 이미 즉시(plain 경로), **이벤트/늪 배너는 1050→650ms**로 줄이고 배너 자체에 미세 모션(슬라이드 인)으로 "멈춤"이 아니라 "전환"으로 읽히게. 속도 옵션(있으면)과 연동.
- **D. 잡기 임팩트는 이미 좋다.** 유지. 다만 잡힌 말이 튕길 때 `screenShake()`(3118)를 큰 잡기(2개+)에만 걸어 과함을 막되, 단일 잡기에도 `pop` 정도는 유지.

**주의(함정 34)**: 방식 2의 rAF는 **말의 SVG `<g>` transform만** 바꾸므로 합성 레이어 친화적이다(화면 전체 transform 아님). `will-change:transform`은 **이동 중에만** 걸고 끝나면 해제(`_armLayer` 패턴, 3105-3111 참고). 판 SVG의 `feDropShadow` 재계산을 유발하지 않도록 말은 그림자 필터가 아닌 미리 그린 반투명 타원(pcshadow)을 쓰는 현 구조 유지. `npm run perf:yut`로 p95 회귀 확인.

## 항목 3. 모바일에서 연출이 실제로 도는가  ★모바일 최우선

### [현재 코드 상태]

- **게이트는 두 겹이다.**
  - **JS 가드** `FX_REDUCED()` (`yut.html:3072`): `matchMedia('(prefers-reduced-motion: reduce)').matches`. 카메라펀치(3113)·스크린셰이크(3118)·플래시(3117)·코인(3155)·이벤트 파티클(3252)·잡기 고스트(3413,3428)·늪(3121,3129) 등 **거의 모든 함수가 `if(FX_REDUCED())return`으로 시작**. `runMoveSequence`도 reduced면 애니 없이 즉시 정착(3670-3675). resultBurst/데일리배너 등은 reduced 분기로 수명만 단축.
  - **CSS 가드** `@media (prefers-reduced-motion: reduce)` (`yut.html:938-956`): 전역 리셋 `*,*::before,*::after{ animation-duration:.001ms !important; transition-duration:.001ms !important }`. 추가로 **`#pieceLayer .pcpiece{ transition:none !important }`(944)** → 말이 순간이동. 스틱 토스·throwmo·VS인트로·콤보·이벤트fx 전부 `animation:none`(940-955, 1130-1136).
- 즉 **reduce가 켜지면: 말은 텔레포트, 윷가락은 안 튀고, 결과 버스트·셰이크·플래시·파티클·콤보·VS인트로가 전부 사라진다.** 남는 건 결과 텍스트, 720ms 지연(항목1의 setTimeout은 가드 밖이라 유지), 진동(buzz는 가드 밖이라 유지), 사운드뿐.

### [딱딱함의 원인]

1. **"재미 반감"이 스위치 하나로 문자 그대로 재현된다.** 사용자 표현이 정확히 이 상태와 일치한다 — 연출의 절반 이상이 애니 기반이고, reduce는 그걸 **전부·한꺼번에** 끈다. 중간 단계(약한 연출)가 없는 **절벽**이다.
2. **모바일에서 reduce가 켜져 있을 현실적 경로가 여럿이다 [확인필요]:**
   - 사용자가 OS 접근성 "동작 줄이기"를 켰을 수 있다(배터리 절약/멀미 방지 목적으로 켜는 사람 많음).
   - 안드로이드 "애니메이션 배율 0"(개발자옵션)·**배터리 세이버**가 일부 웹뷰에서 reduce로 전달되는 사례.
   - Capacitor 앱 웹뷰/특정 브라우저의 기본값 편차.
   - 함정 7: 헤드리스는 기본이 reduce라 검증에서 이미 이 사각지대를 경험함.
3. **단, 사용자 단어가 "딱딱하다(기계적)"이지 "아무것도 안 움직인다"가 아니므로**, reduce가 확실한 범인이라기보단 **모션이 켜진 상태의 로봇 이동(항목2)과 병렬 위험**으로 봐야 한다. 그래서 둘 다 최우선으로 다룬다.

### [개선안]

- **A. 실제 사용자 상태를 먼저 측정한다(진단).** 배포본에 1회성 로그/계측: 진입 시 `matchMedia('(prefers-reduced-motion: reduce)').matches`와 `navigator.userAgent`를 analytics 커스텀 속성으로. "우리 유저 중 몇 %가 reduce인가"를 알면 이 항목의 우선순위가 확정된다. (analytics.js 규칙 준수 — 게임 로직 불간섭, try/catch.) [확인필요]를 데이터로 해소.
- **B. "절벽"을 "완만한 경사"로 바꾼다 — reduced에서도 최소 juice.** 접근성 원칙(큰 화면 이동/회전/시차 제거)은 지키되, reduce에서 **① 말은 순간이동 대신 짧은 크로스페이드/`opacity`+120ms 정도의 짧은 이동**(전정계 자극 없는 소폭), **② 결과는 정적 팝 대신 스케일 1.0→작은 펀치(≤150ms)**, **③ 진동/사운드는 지금처럼 유지**. WCAG는 "모든 모션 금지"가 아니라 "과한 전정 자극 제거"이므로 절제된 페이드/펀치는 허용된다.
- **C. reduced 전용 대체 연출 경로를 명시한다.** 현재는 `if(FX_REDUCED())return`으로 "아무것도 안 함"이 대부분. 대신 핵심 순간(윷/모/잡기/완주/승리)만 **reduced 대체 연출 함수**로 라우팅(짧은 텍스트 카운트업 + 진동 + 사운드). 화면 흔들림/시차/큰 이동만 빼면 "밋밋"에서 "담백하지만 반응함"으로.
- **D. 배터리 세이버 오탐 방지.** reduce=true여도 사용자가 게임 설정에서 "연출 켜기"를 명시하면 존중하는 토글 고려(상단바 이미 소리/BGM 토글 있음, 2504-2588 패턴 재사용). 접근성 기본은 존중하되 탈출구 제공.

**주의**: B/C/D는 **접근성을 깨면 안 된다.** reduce 사용자에게 큰 이동/회전/플래시를 되살리는 게 아니라, **작고 짧은 반응**만 추가하는 것. `scripts/browser-test`의 `setMotion(false)` 경로(함정 7)로 reduced 렌더를 회귀 검증할 것.

## 항목 4. 터치 피드백·햅틱·사운드

### [현재 코드 상태]

- **햅틱**: `buzz(p)=navigator.vibrate(p)` (`yut.html:2489`). 걸려 있는 곳:
  - `toss` 18ms(2492), `capture` [25,30,45](2494), `win` [60,50,70,50,140](2495), `lose` [70,60](2496), `yut` [30,20,50](2498), `finish` [40,40,90](2499), `backdo` [15,50,15](2500), 그리고 내 차례 알림 `notifyTurn` 180ms(2597, 온라인·백그라운드 탭용).
  - **음소거와 무관하게 유지**(soundOn 가드 밖) — 좋은 설계.
- **버튼 눌림 피드백**: `.bigbtn:active{ transform:scale(.96) }`(784), `.bigbtn.ready{ btnpulse }`(788). `.btn`도 `transition:transform .09s`(311).
- **사운드**: WebAudio 합성(2475-2503). 나무 딱소리(woodClack)·타격감·리버브·리미터. `move()`(square 660Hz, 2493), `pop/ding/finish/gold` 등. 기본 켜짐(`soundOn`, 2472).

### [딱딱함의 원인]

1. **말 이동에 진동/타격 사운드가 사실상 없다.** `move()`(2493)가 정의돼 있으나 일반 hop 착지에서 호출되는 경로가 안 보인다 [확인필요] — `slideAlong`/`runMoveSequence`(3626-3701)에 `SFX.move` 호출이 없다. 이동은 게임에서 가장 자주 일어나는 동작인데 **가장 자주 하는 행동에 손맛이 없다.** 항목2와 겹치는 핵심.
2. **차징(꾹 누름)에 촉각 상승 신호 없음.** 항목1-2와 동일.
3. **햅틱 자체가 안 걸릴 수 있다 [확인필요].** iOS Safari는 `navigator.vibrate`를 **지원하지 않는다**(전부 무시). 안드로이드 크롬은 지원하지만 **사용자 제스처·사이트 설정에 따라 무시**될 수 있고, PWA/웹뷰마다 편차. 즉 아이폰 사용자에겐 진동 손맛이 0. → 아이폰에서는 **시청각 피드백이 더 촘촘해야** 진동 부재를 메운다.
4. **버튼 외 요소의 터치 피드백 부재.** 말 탭·목적지 고스트 탭(stepghost) 등 인터랙션 순간에 눌림감(스케일/링 플래시)이 옅다.

### [개선안]

- **A. 이동 착지에 사운드+진동 연결**(항목2-B와 통합): hop마다 옅은 `move()` 또는 도착에 한 번 "탁" + `buzz(12)`. 가장 잦은 동작에 손맛을 주는 게 체감 대비 저비용.
- **B. iOS 폴백 전략.** 진동이 없는 기기를 감지(간접: iOS UA 또는 `vibrate` 반환값)해 **핵심 순간의 시각 펀치/사운드를 살짝 강화**. 진동에 의존한 payoff를 시청각으로 이중화.
- **C. 인터랙티브 요소 눌림감 통일.** 말/고스트/칩 탭에 `:active` 스케일 + 링 플래시(이미 `.bigbtn:active`가 있는 패턴 확장). 터치 다운 즉시 반응(포인터다운에 시각 반응) → "반응이 빠른" 느낌.
- **D. 차징 틱**(항목1-A). 

**주의**: 진동 패턴을 과하게 늘리면 배터리·거슬림. 현 짧은 패턴 기조 유지. 사운드 추가는 리미터(2480)가 이미 클리핑을 막지만 이동 사운드는 **아주 작게**(겹침 대비).

## 항목 5. 템포·전환

### [현재 코드 상태]

- **AI 사고 지연** `aiMs=900ms`(`yut-core.js:175`, 사용 654). throw 단계 900ms 후 던지고(660-669), move 단계 900ms 후 이동(670-678). `aiFast`면 130ms(654), 시뮬은 0.
- **결과 공개 지연** 720ms(`yut.html:4262` setTimeout).
- **이동 후 정지** `MOVE_PAUSE=1050ms`, 배너 `BANNER_MS=1150`(3460).
- **판 시작 시퀀스**: VS 인트로 ~960ms(3206) → 선뽑기 → 데일리 배너 1150ms 지연 후 2800ms(3230,3239). 판 시작에 연출이 겹겹.
- **턴 전환 안내**: `turnInfo`가 "상대의 차례 · 던지는 중" 등 텍스트 갱신(4077). 내 차례엔 버튼 `ready` 펄스(4059).

### [딱딱함의 원인]

1. **AI 차례에 "생각 중" 능동 피드백이 없다.** AI가 던지기까지 900ms 동안 화면은 아바타 idle bob(693)만. 던지고 나선 다시 900ms 정지 후 이동. **아무 일도 안 일어나는 900ms×2가 "멈춘 것 같은" 순간**을 만든다. 넷마블은 이 구간에 "윷 흔드는" 루프 모션/사운드를 넣어 죽은 시간을 채운다.
2. **대기 시간의 총합이 크다.** 한 AI 턴 최악: 900(사고) + 720(결과) + 900(사고) + 이동(최대 1500) + 1050(pause) ≈ **5초에 사용자 입력 0.** 다인전이면 내 차례가 한참 안 온다 → "답답/딱딱."
3. **전환이 "정지→정지"다.** 턴이 넘어갈 때 부드러운 하이라이트 이동이 아니라 텍스트/클래스가 툭 바뀐다. 현재 차례 플레이어 스트립 강조 전환에 모션 부재.

### [개선안]

- **A. AI 사고 구간을 채운다(체감 큼).** AI throw 대기(900ms) 동안 **윷가락 흔들기 루프**(작은 진동 모션)나 던지는 캐릭터의 준비 모션 + 옅은 사운드. "생각 중… 툭!"의 리듬. reduced에선 텍스트 "…"만.
- **B. aiMs 차등·단축.** 일반 이동 판단은 900→550ms 정도로, 큰 판단(잡기 가능)만 길게. `aiFast` 경로가 있으니(654) 난이도/속도 옵션과 연결. 단, 너무 빠르면 "휙 지나가 못 봤다"가 되므로 결과 payoff(720ms)는 유지.
- **C. MOVE_PAUSE 축소·모션화**(항목2-C 재확인). 1050→650, 배너는 슬라이드-인으로 "전환"화.
- **D. 턴 전환 마이크로 연출.** 현재 차례 표시(스트립/배너)가 **부드럽게 슬라이드/글로우 이동**하도록. `turnInfo` 갱신 시 짧은 펄스. 넘어가는 리듬이 살아난다.
- **E. 내 차례 진입 강조.** 온라인 `notifyTurn`(2597)은 백그라운드 탭용. **포그라운드에서 내 차례가 오는 순간**에도 버튼 ready 펄스 외에 짧은 `buzz`+사운드+`turnInfo` 하이라이트로 "네 차례!" 전환을 분명히.

**주의**: 대기 축소는 **가상 시계 밸런스 시뮬**(`npm run sim:balance`)과 무관(연출/사고 지연은 판 길이 판정에 가상시계로 흡수됨, 함정 밸런스 섹션). 다만 aiMs를 바꾸면 온라인 서버 authoritative 엔진에도 반영되니(서버가 core를 require) **드리프트 주의 — core만 고치고 `npm run build`**(함정: 엔진 이중구조).

## 개선 시 반드시 지킬 것 (성능 예산·접근성·아키텍처)

1. **성능 예산(함정 34, `npm run perf:yut` / `npm run phone:perfyut`).** 
   - 말 이동 rAF는 **말의 SVG `<g>` transform만** 건드릴 것(화면 전체 transform 금지 — camerapunch/scrshake가 재래스터로 렉을 만든 전례). `will-change:transform`은 **이동 중에만** 걸고 끝나면 해제(`_armLayer` 3105-3111 패턴).
   - 판 SVG `feDropShadow` 재계산 유발 금지 — 말 그림자는 현 `pcshadow`(미리 그린 반투명) 유지.
   - 파티클/트레일 개수는 `window.innerWidth<=480`에서 줄이는 현 기조(3091) 유지.
   - 변경 후 실기기 p95(현 목표 ~14ms대) 회귀 확인.
2. **reduced-motion 접근성.** reduce에 큰 이동·회전·플래시·시차를 **되살리지 말 것.** 추가하는 건 "작고 짧은(≤150ms) 페이드/펀치 + 진동/사운드"뿐. `scripts/browser-test`의 `setMotion(false)`로 reduced 경로를 회귀 검증(함정 7). CSS 전역 리셋(938)을 무력화하려면 개별 선택자로 명시적 예외를 두되 최소화.
3. **엔진 이중구조/드리프트(함정 이중구조 섹션).** `aiMs` 등 **엔진 값은 `yut-core.js`만 고치고 `npm run build` → `npm run check:drift`(10종 OK)**. HTML의 `CORE:x` 마커 블록 직접 수정 금지. 연출/렌더(SFX·slideAlong·CSS)는 HTML의 마커 바깥이라 평소대로 수정.
4. **연출 검증은 DOM/계측으로(함정 32).** 눈으로 스크린샷 대신 `verify-fx.js`·MutationObserver·`getAnimations()`로 "실제로 돌았나"를 세라. 헤드리스 기본 reduce 함정(7) 유의 — `setMotion(true)`로 모션 경로, `setMotion(false)`로 접근성 경로 둘 다 확인.
5. **계측 규칙(analytics.js).** reduced 실사용률 측정은 `try{window.AL&&AL...}catch(e){}`로 감싸 게임 로직 불간섭. 커스텀 속성은 요금제상 대시보드에 안 보일 수 있음(보너스 취급).
6. **온라인 일관성.** 이동 연출은 클라 전용이라 서버와 무관하지만, `aiMs`·엔진 타이밍을 바꾸면 서버 authoritative 엔진에도 반영되므로 `test:online`/`test:cardonline`류 회귀 확인.
