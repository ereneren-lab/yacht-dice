## 1. 제작 목표

Phase 1(BX 기반)을 마무리하는 **의미 기반(semantic) 디자인 토큰 체계**를 확정한다. 지금은 A(정제·에스프레소+골드)의 값으로 즉시 출시하고, 이름은 한 번만 세워 나중에 B(설화 야시장)가 **같은 이름에 값만 갈아끼워** 얹히도록 설계한다. 산출물은 코드로 바로 옮길 수 있는 표와, 안전하게 추가 가능한 신규 파일 `public/tokens.css` 초안이다.

## 2. 적용 전략 (요약)

- 브랜드 방향: **절충안** — A값(에스프레소 골드)으로 지금 위계·신뢰도를 회복하고, B(인디고 밤하늘·등불 주황·옥색·진홍)는 이름을 안 바꾼 채 값·에셋만 나중에 얹는다.
- 서비스명: **"딱세판만"** 확정. "주사위 골목"은 세계관 배경어로만 유지(리네이밍 없음, 계측 히스토리 보존).
- 핵심 설계 원리: **토큰 이름은 한 번만 정의, 값은 테마/시즌별로 교체.** B가 켤 자리(`--accent`)는 지금 예약해 두되가 값은 A 톤으로 채운다.

## 3. 크리에이티브 방향

- "화면에서 골드가 보이는 총량은 줄이지 않되, **의미를 분리**한다" — 브랜드/CTA(`--brand-gold`) vs 재화(`--coin`) vs 정보(중립 `--ink`)를 색으로 구분해 위계를 세운다.
- "이름은 세계 하나, 조명은 세 가지" — 3테마(에스프레소/흑임자/한지)는 A에서는 "다른 조명", B가 얹히면 "하루의 세 시간대"라는 서사로 이어진다. 이번 문서는 그 이야기가 깨지지 않도록 토큰 이름을 설계한다.
- "코드에 이미 있는 것부터 살린다" — 아래 4절에서 확인하듯, `--gold`라는 이름의 토큰이 이미 7개 파일에 존재한다. 새로 만드는 게 아니라 **이미 시작된 분리를 완성**하는 작업이다.

## 4. 코드 실측 — 착수 전 확인한 사실 (모든 값의 근거)

리서치 문서(8/11)가 "8곳에서 `--brass` 하나가 겸직"이라고 요약했는데, 실제로 `public/index.html` 하나에서만 `var(--brass)`가 **40회 이상** 쓰인다(로고~통계바~폼 포커스까지). 그리고 전략 문서가 상정한 "카드/카지노 팔레트가 다르다"는 사실 확인 결과 아래처럼 더 구체적이었다.

### 4-1. [확정] `--gold`는 이미 존재하는 "코인" 토큰이다 — 그런데 절반만 배선돼 있다

`--gold`라는 이름이 이미 아래 7개 파일의 `:root`에 있고, 실제로 **코인 숫자·판돈(pot)·내 차례 강조·승리 글로우**에 쓰이고 있다(=`--coin` 역할을 이미 하고 있음):

| 파일 | espresso `--gold` | hanji `--gold` | sesame `--gold` |
|---|---|---|---|
| seotda / oldmaid / blackjack / baccarat / highlow / indianpoker / onecard | `#f0c65a` (7파일 동일) | `#a67613` (7파일 동일) | **정의 없음**(gap) |
| alkkagi | `#e0a23c` ⚠️ `--brass`와 완전히 같은 값 — 이름만 분리, 실질 구분 없음 | `#a67613` | 정의 없음 |
| yacht | `#e8a13a` | `#c8842a` | `#e8e2d4` |
| shop | `#f0c65a` | `#7d5809` | `#e0d6b0` |
| **index.html(허브)** | **정의 자체가 없음** — `.coinbar b{color:var(--gold,#d8a93a)}`로 **하드코딩 fallback**만 씀 | 위와 동일(fallback 고정) | 위와 동일(fallback 고정) |

**의미**: 허브의 코인 숫자 색은 테마를 바꿔도 **절대 안 바뀐다**(항상 `#d8a93a`) — 3테마 인프라가 있는데 코인 색만 거기 참여를 안 하고 있다. `shop.html`은 반대로 3테마 전부에서 `--gold`를 정의한 **가장 성숙한 참고 파일**이다.

### 4-2. [확정] "카드/카지노 2계층"이 아니라 사실상 "카드군 7파일이 완전히 동일한 팔레트"다

`seotda·indianpoker·onecard·oldmaid·blackjack·baccarat·highlow` 7개 파일의 `:root`가 **글자 하나까지 동일**하다(`--bg:#12210f; --ink:#f2e9d6; --muted:#9db089; --panel:#1c2f18; --panel2:#274023; --line:#2f4a28; --brass:#d9b35a; --gold:#f0c65a; --danger:#e8696b; --felt:#1f5c2e; --felt2:#164322; --chip:#e8c15a;`). 리서치 문서가 "카지노 3종은 별도 팔레트"라고 적었던 건 8/5 시점 사실이고, 지금은 **7파일이 이미 통일**돼 있다 — 다만 허브·보드게임군과는 여전히 분리돼 있다.

**⚠️ 신규 발견 — 이 7파일은 `sesame`(흑임자) 오버라이드가 전혀 없다.** 사용자가 허브에서 흑임자를 고르고 섯다·블랙잭 등에 들어가면, `data-theme="sesame"`가 매칭되는 CSS 규칙이 없어 **그냥 espresso 값(짙은 녹색 펠트)이 그대로 보인다.** 3테마 중 1개가 카드군 7종에서 조용히 무력화돼 있다는 뜻이다.

### 4-3. [확정] 브랜드 강조색 이름이 파일마다 다르다 — `--brass` vs `--accent`

- 허브 + 보드 6종(yut/kb/ld/lcr/alkkagi 는 `--brass`) — `yacht.html`만 **`--accent`/`--accent-ink`**로 같은 역할을 부른다(`yacht.html:35`). 이미 `scripts/audit-tokens.js`의 `CHECKS`가 `--accent`를 따로 감시하고 있다(37번 줄) — 즉 이 이름 불일치는 기존 감사 인프라도 이미 알고 있는 부채다.
- **이건 이번 작업에 직접 영향을 준다**: 브리프가 B를 위해 예약하려는 `--accent`라는 이름을 **`yacht.html`이 이미 다른 뜻(=브랜드 골드의 별칭)으로 선점**하고 있다. `yacht.html`을 손대지 않고 새 `--accent`(옥색 예약)를 선언하면, 그 파일 안에서 두 가지 다른 의미의 `--accent`가 충돌한다. → 5절에서 이관 원칙으로 명시.
- `yacht.html`은 또한 `data-theme="excel"`/`"photoshop"`(위장 모드로 추정)까지 같은 변수셋을 오버라이드하고 있다(`yacht.html:478,645`) — 이 파일이 토큰 체계에서 가장 특이한 파일임을 감안해야 한다.

### 4-4. [확정] 텍스트-온-골드 색(`--brass-ink`)이 다크 테마에서 정의돼 있지 않다

`--brass-ink`는 **한지(라이트) 테마에서만** `#fff8ec`로 정의된다(`index.html:80`, `yut.html`, `kb.html` 등 동일). 에스프레소/흑임자(다크) `:root`에는 `--brass-ink`가 아예 없다. `yut.html:110`처럼 `.btn{background:var(--brass);color:var(--brass-ink)}`를 쓰는 파일은 다크 테마에서 **정의되지 않은 커스텀 프로퍼티**를 참조하게 되어, 텍스트 색이 "의도"가 아니라 **상속(대개 `--ink`의 크림색)으로 우연히** 결정된다. 크림(`#f3ece0`) 글자를 밝은 골드(`#e0a23c`) 배경에 얹으면 대비가 약할 수 있다[확인필요, 대비 계산 필요] — 반면 `kb.html:252`처럼 `color:var(--bg)`(거의 검정)를 쓴 파일은 우연히 안전하다. **같은 컴포넌트(`.btn`)가 파일마다 다른 방식으로 이 문제를 피하거나 안 피하고 있다** — 의도된 시스템이 아니라 각자 손으로 맞춘 결과다.

### 4-5. [확정] 서피스 토큰(`--bg/--panel` 등)까지 게임마다 하드코딩돼 있다 — `--felt`만의 문제가 아니다

전략 문서가 `seotda.html`을 예로 들었는데, 실제로는 **카드군 7파일 + alkkagi + yacht**가 전부 자기 `--bg/--ink/--muted/--panel/--panel2/--line`을 따로 정의한다. `--felt`(테이블 표면)만 다른 게 아니라 **앱 크롬 색 전체**가 다르다 — 이게 3-8 원칙("앱 크롬은 하나, 테이블만 개성")이 아직 코드에 반영 안 됐다는 확정적 증거다.

### 7-2. 파일별 "무엇을 지우고 무엇을 상속시키는지" 세부 지시

- **공통 절차(13파일 전부)**: 각 파일의 `<style>` 블록 맨 위에 `tokens.css`를 앞세운다(`@import url('tokens.css');` 또는 빌드 시 `<link>` — 실제 배선 방식은 Orchestrator가 `npm run build`/`check:drift`와 함께 결정). 그 다음 자체 `:root{...}` 블록에서 **5-1·5-2절 표에 이름이 있는 토큰**을 전부 삭제한다. 남기는 건 5-3절의 게임 전용 토큰과 6-3절의 `--felt` 계열뿐이다.
- **`seotda.html` 구체 예(사용자 브리프가 지목한 파일)**: 지금 `:root{ --bg:#12210f; --ink:#f2e9d6; --muted:#9db089; --panel:#1c2f18; --panel2:#274023; --line:#2f4a28; --brass:#d9b35a; --gold:#f0c65a; --danger:#e8696b; --felt:#1f5c2e; --felt2:#164322; --chip:#e8c15a; }`(seotda.html:38-41) 중 → **지울 것**: `--bg, --ink, --muted, --panel, --panel2, --line, --brass, --danger` (8개) · **`--gold`→`--coin`으로 이름만 바꿔 유지**(값은 5-2절 표) · **상속시킬 것**: `tokens.css`의 동일 이름 토큰 · **남길 것**: `--felt, --felt2, --chip`. `html[data-theme="hanji"]{...}` 오버라이드 블록(seotda.html:42)도 같은 원칙으로 축소하고, **sesame 오버라이드는 새로 안 만들어도 된다**(`tokens.css`가 대신 처리).
- **`yacht.html` 전용 주의**: `--accent/--accent-ink`→`--brand-gold/--brand-gold-ink`, `--ai`→`--opp`로 **개명**(단순 삭제가 아니라 파일 내 참조부도 함께 바꿔야 함 — 6-4). `data-theme="excel"/"photoshop"` 오버라이드는 브랜드 토큰이 아니라 위장 모드 전용이므로 이번 이관과 무관, 손대지 않는다.
- **검증 의존성**: 이관 후 반드시 `npm run audit:tokens`(값 분산이 의도된 것인지 확인) → `npm run build` → `npm run check:drift` 순으로 Orchestrator가 확인. `audit-tokens.js`의 `CHECKS`/`ALLOW`(scripts/audit-tokens.js:34-60)는 아직 `--gold`/`--coin`/`--felt`를 감시하지 않으므로, 이관이 끝나면 그 스크립트에 새 항목을 추가하는 후속 작업이 필요하다[다음 단계, 이 문서 범위 밖].

## 8. 필수 요구사항 4 — 절충 로드맵 (A-now / B-later)

핵심 증명: **아래 표의 "토큰 이름" 칸은 A열과 B열에서 한 글자도 안 바뀐다.** 바뀌는 건 "값" 칸뿐이다.

| 토큰 | A-now (지금 출시) | B-later (야시장 레이어 얹을 때) | 트리거 |
|---|---|---|---|
| `--brand-gold` | `#e0a23c`(에스프레소) | `#ffb454`(등불 주황) | 값 교체 |
| `--brand-gold-ink` | `#15110d` | `#241606`[제안, B팔레트 어두운 계열] | 값 교체 |

**B가 새로 추가하는 것(A에는 없던 이름)**: `--coin-d`의 B용 파생값, 마스코트 배경 글로우 색(게임별 앰비언트) 등은 **새 토큰**이 필요할 수 있다 — 이건 "값 교체"가 아니라 "신규 추가"이므로 B 착수 시점에 별도 설계가 필요하다[미확정, B 승인 후].

### 8-1. `data-theme` 별도 테마 vs 기본값 진화 — 권고

**권고: 기본값 진화(오버레이 방식) — 별도 `data-theme="yasi"`를 만들지 않는다.**

근거:
1. 지금의 3테마(`espresso/sesame/hanji`)는 이미 "다크·다크알트·라이트"라는 **밝기 축**으로 존재한다. B가 4번째 `data-theme` 값으로 추가되면, 유저는 "밝기를 고르는 스위치"와 "세계관을 고르는 스위치"가 하나로 뒤섞여 보인다 — 지금 코드가 `alley_theme` 키 하나로 밝기 3종을 저장하는 구조(`index.html:865`)와 충돌한다.
2. `yacht.html`에 이미 `data-theme="excel"/"photoshop"`(위장 모드로 추정)이라는 **네 번째 이상의 값**이 실존한다(4-3 근거). 이건 "테마 선택 UI에 노출되지 않는 특수 모드"다. B를 같은 속성값 슬롯에 넣으면 이 위장 모드 처리 로직(`html[data-theme="excel"] .excel-tip{display:none}` 류)과 새 값이 우연히 겹치지 않는지 매번 확인해야 하는 부담이 생긴다.
3. 절충안의 핵심 문지가 "값만 바꾼다"인데, 오버레이 방식(에스프레소 자체의 값이 진화)이 그 원칙을 코드로 가장 직접적으로 구현한다 — `tokens.css`의 `:root` 한 블록의 HEX만 바꾸면 끝난다. 별도 `data-theme`를 만들면 그 블록을 **복제**해야 하고, 복제는 이번 리서치가 지적한 "3계층 분리" 문제를 브랜드 레이어에서 재현하는 것과 같다.
4. 다만 **B가 승인되어도 "즉시 전면 전환"이 리스크가 크다고 판단되면**, 잠정적으로 `data-theme="yasi"`를 **베타/시즌 한정 오버레이**로 병행 운영하는 절충의 절충도 가능하다 — 이 경우에도 토큰 이름은 그대로이므로 나중에 기본값으로 승격하는 전환 비용이 0에 가깝다. 즉 **이름 설계가 두 진화 경로 모두를 이미 지원**하므로, "당장 결정"이 아니라 **"B 착수 시점에 결정해도 늦지 않다"**[제안].

## 9. 필수 요구사항 5 — 컴포넌트 토큰 원칙

실제 픽셀 값이 아니라 "어떤 토큰을 쓰고 무엇을 금지하는지"만 규정한다(요청 범위).

| 컴포넌트 | 현재 혼란 [확정] | 원칙 |
|---|---|---|
| **버튼(1차 CTA)** | `.btn`이 배경에 `--brass`(yut/kb 등) 또는 `--accent`(yacht)를 섞어 씀 | 배경 `--brand-gold`→`--brand-gold-d` 그라디언트, 텍스트 `--brand-gold-ink`(색 이름으로만 지정, HEX 직접 금지). 파일마다 다른 변수명(`--accent` 등) 사용 금지 — 반드시 `--brand-gold` 계열만. |
| **버튼(선택형 — `.opt`, `.chips button`)** | 기본 배경 `--panel2`, 활성 시 `--brass` 혼용 | 비활성 `--panel2`+`--line` 테두리. 활성 `border-color:--brand-gold; color:--brand-gold; background: color-mix(--brand-gold 15%, --panel2)` — 6-2의 "E. 인터랙션 상태" 규칙과 동일 계열. `.btn`과 `.opt.on`이 **같은 토큰을 쓰되 강도(퍼센트)만 다르게** 해 "버튼 계열이라는 걸 색으로 알 수 있게" 한다. |
| **카드(`.gcard`/`.sheet`/`.panel` 혼용)** | 세 클래스가 배경·테두리를 각자 정의 | 배경은 항상 `--panel`(강조 필요 시 `--panel2`), 테두리는 항상 `--line`. 브랜드색 테두리는 `:hover`에서만 `color-mix(--brand-gold, --line)`로 허용(6-2 "D. 장식" 규칙). 카드 자체의 배경에 브랜드색을 직접 칠하는 것은 금지(카드가 배지처럼 보여 위계가 무너진다). |
| **배지/pill** | `played`, `statbadge`, `achbadge`, `cnt` 등이 전부 `--brass` 텍스트+배경 | 정보성 배지(카운트·상태)는 `--ink`/`--muted` 텍스트, 테두리만 흔적. **보상성 배지만**(달성한 업적·레벨업) `--coin` 사용 가능 — "이걸 얻었다"라는 뜻일 때만 코인 색. |
| **상단바** | 아이콘 7~10개, 제목 잘림(함정 25) | 이 문서 범위 밖(레이아웃 문제)이나, 상단바 강조 요소(활성 탭 등)는 `--brand-gold` 계열만 — 새 색 도입 금지. |
| **아바타(마스코트)** | 게임별로 이모지 기본값 vs `chars.js` 마스코트 혼재 | 토큰 관점에선 아바타 프레임 테두리(선택됨 표시)를 `--brand-gold`로 통일. 마스코트 자체를 기본값으로 승격하는 로직 변경은 이번 문서 범위 밖(전략 문서 3-5 참고, 별도 production 작업). |
| **셋업 시트** | `.sheet`가 파일마다 배경·라벨색 산재 | 배경 `--panel`, 라벨 `--ink`(섹션 라벨에서 골드 제거 — 6-1 규칙과 동일), "시작" 버튼만 `--brand-gold`. |

**금지 규칙(공통)**: ① HEX를 컴포넌트 CSS에 직접 쓰지 않는다(전부 `var(--토큰)`) ② `--brass`/`--accent`/`--gold`라는 옛 이름을 새 컴포넌트에 쓰지 않는다(이관 완료 파일 기준) ③ 정보성 텍스트(라벨·통계)에 브랜드색을 쓰지 않는다 — 숫자를 강조하려면 굵기·크기를 먼저 쓴다.

## 10. 필수 요구사항 6 — 게임 아이콘 시스템 규칙

- **실제 아이콘 아트(13종 모노라인 글리프) 제작은 이번 범위 밖** — 전략 문서 3-5절이 정의한 방향(이모지 대체, 획 두께 통일, `--brand-gold` 단색 또는 `--ink`)을 따르는 별도 production 작업으로 넘긴다.
- **코드 상수 위치 권고**: 신규 파일 `public/game-icons.js`를 만들어 `public/analytics.js`의 `GAMES` 표(analytics.js:98-112)와 **같은 13개 키 순서**로 아이콘 매핑을 둔다.
  ```js
  // public/game-icons.js (신규, 이번 범위 밖 — 형태 예시만 제시)
  // ⚠️ analytics.js의 GAMES 표(98~112줄)와 반드시 같은 13개 키를 유지할 것.
  //    한쪽만 고치면 함정 28(8종이 조용히 '허브'로 집계됐던 사고)과 같은 종류의 드리프트가 난다.
  var GAME_ICON = {
    'yut':'icon-yut', 'yacht':'icon-yacht', 'kb':'icon-kb', 'ld':'icon-ld', 'lcr':'icon-lcr',
    'alkkagi':'icon-alkkagi', 'seotda':'icon-seotda', 'indianpoker':'icon-indianpoker',
    'onecard':'icon-onecard', 'oldmaid':'icon-oldmaid', 'blackjack':'icon-blackjack',
    'baccarat':'icon-baccarat', 'highlow':'icon-highlow'
  };
  ```
  같은 파일에 두지 않고 별도 파일로 둔 이유: `analytics.js`는 계측 코드라 아이콘(순수 UI 데이터)을 얹으면 관심사가 섞인다. 대신 **"GAMES 표 옆에 나란히 두라"는 요청의 의도**(같은 자리에 두면 실수 확률이 낮다)는 `game-icons.js`를 `analytics.js`와 같은 디렉터리·같은 13-키 순서로 유지하는 것으로 satisfies한다. Orchestrator가 실제 파일 추가를 결정할 때 이 방식과 "analytics.js 안에 직접 추가" 방식 중 택일하면 된다 — 후자를 택하면 `GAMES` 정의 바로 다음 줄(analytics.js:113 앞)에 넣을 것.
- **아이콘 색 토큰**: 허브 카드·상단바 모두 `--brand-gold` 단색 또는 `--ink`만 사용(9절 금지 규칙과 동일). 게임별로 다른 색을 넣지 않는다 — "13개가 한 세트"라는 신호가 아이콘 색 통일에서 나온다.

## 11. 필수 요구사항 7 — 파일럿 권고

### 11-1. 추천: **`index.html`(허브) 색 역할 분리 + `seotda.html`(섯다) `:root` 이관**

**이유**:
1. `index.html`은 골드 위계 문제가 **가장 크게 드러나는 파일**(40여 곳, 6-2절)이자 **모든 유저가 반드시 지나가는 진입점**이다 — 여기서 위계가 정리되면 체감 효과가 즉시 전체 서비스 인상에 반영된다.
2. `seotda.html`은 사용자 브리프가 직접 예로 든 "`:root` 하드코딩" 대표 사례이고, **카드군 7파일과 완전히 동일한 팔레트**(4-2절)를 쓰므로, 섯다 하나를 이관하면 **나머지 6파일(인디언포커·원카드·도둑잡기·블랙잭·바카라·하이로우)에 그대로 복제할 수 있는 템플릿**이 확보된다 — 파일럿 1개의 검증 효과가 7파일로 즉시 파급된다.
3. 섯다는 현재 **sesame 테마가 무력화**된 상태(4-2절)라, 이관만으로 버그 하나(테마 3종 중 1종 미반영)가 **부작용 없이 저절로 고쳐지는지**를 검증할 수 있는 좋은 시험대다.

**정확한 변경 목록**:

**A) `index.html`**
- `.brand h1 .en`(102), `.tilehead b`(141), `.cat-h .cnt`(212), `.allgames .agn`(505), `.qh`(467): `var(--brass)` → `var(--ink)`
- `.coinbar b`(444): `var(--gold,#d8a93a)` → `var(--coin)` (3테마 반응 복구)
- `.levelcard .lv-top span`(345), `.lv-bar i`(347): `var(--brass)`/`var(--brass-d)` → `var(--coin)`/`var(--coin-d)`
- 로고(93-94), CTA류(111,113,126,245,253-254,307): `var(--brass)`/`var(--brass-d)` → `var(--brand-gold)`/`var(--brand-gold-d)` (이름만 교체, 값 동일이라 시각적 변화 없음 — 안전한 리팩터)
- 나머지 장식성 테두리(216,294,370-371,403,406,432,472 등): `color-mix(in srgb,var(--brass) N%,...)` → 동일 패턴에서 `--brass`만 `--brand-gold`로 치환

**B) `seotda.html`**
- `:root`(38-41)에서 `--bg, --ink, --muted, --panel, --panel2, --line, --brass, --danger` 삭제(→`tokens.css` 상속)
- `--gold` → `--coin`으로 참조명 일괄 치환(파일 내 `var(--gold)` 전체 — 74,80,87,118,120,130,133-136,141,144,165,188,190,219,242,1553,1628행)
- `--felt, --felt2, --chip`은 그대로 유지
- `html[data-theme="hanji"]{...}`(42) 오버라이드에서 `tokens.css`가 이미 처리하는 토큰(`--bg/--ink/--muted/--panel/--panel2/--line/--brass/--danger`) 제거, `--gold`→`--coin`, `--felt/--felt2` 유지
- **sesame 오버라이드는 추가하지 않는다** — `tokens.css`가 자동으로 채운다(검증 포인트)

**검증 기준**: 이관 후 ① 허브를 흑임자로 바꾼 채 섯다에 들어갔을 때 배경이 실제로 흑임자 색으로 바뀌는지(현재는 안 바뀜) ② 코인 숫자가 3테마 모두에서 육안으로 다른 색인지 ③ `npm run audit:tokens`가 새로 생긴 값 차이를 ALLOW 목록 없이 실패로 잡는지 확인하고, 실패하면 스크립트의 `ALLOW`에 의도를 기록(또는 값을 맞춤).

## 15. 검수 결과 (자체)

- **목표 적합성**: 7개 필수 요구사항 전부 채움. 토큰표는 3테마 HEX로 완성돼 그대로 CSS화 가능. ✅

## 16. 미확정 사항

- [확인필요] `--coin`(흑임자 `#e4d9a8`), `--warn`(3테마 전부), `--brand-gold-ink`(에스프레소/흑임자 신규 정의) — 실제 WCAG 대비 수치 미계산. 특히 `--brand-gold-ink`는 4-4에서 발견한 기존 버그(다크 테마에서 정의 자체가 없던 문제)를 고치는 값이라 **실측 없이 배포하면 새 버그로 바뀔 위험**이 있다.
- [확인필요] 알까기 `--board`→`--felt` 개명이 실제로 알까기 코드 내 다른 참조(JS의 보드 렌더링 로직 등)에 영향이 없는지 — 이 문서는 CSS 변수명만 봤고 JS 참조는 안 봤다.
- [미확정] 8-1절의 "기본값 진화 vs 별도 테마" 권고는 B 착수 시점까지 결정을 미뤄도 된다고 판단했으나, 이건 이 문서의 판단이며 사용자 재승인 대상.
- [미확정] `--coin-d`의 정확한 파생 공식(브랜드골드 대비 몇 % 어둡게인지)은 제안 수준이며 실제 그라디언트 시각 검토가 필요.
- [범위 밖, 명시] 게임 아이콘 13종 아트, 마스코트 기본 아바타 승격(로직 변경), 로고마크 제작, `scripts/audit-tokens.js`의 CHECKS 확장 — 전부 이번 문서가 가리키기만 하고 실행하지 않음.
